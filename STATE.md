- 2026-08-19: **Whole repo was committed with CRLF line endings — now normalized to LF (commit a009577).** *The lesson:* the previous machine committed Windows line endings into git, which Python and Dockerfiles tolerate but **shell scripts do not**: the shebang `#!/usr/bin/env sh` became `#!/usr/bin/env sh\r`, so `env` failed with `env: 'sh\r': No such file or directory` at container start — before the entrypoint's `mkdir` or `exec "$@"` ever ran. The container build succeeded (Dockerfile parser strips `\r`); only runtime blew up. The "no dirs" symptom was doubled: the entrypoint crashed before its startup `mkdir`, AND the compose volume `./uploads:/app/uploads` shadows whatever the Dockerfile `RUN mkdir -p` created at build time — so a container sees only what the *entrypoint* creates. **Prevention:** `.gitattributes` at repo root with `* text=auto eol=lf` + `git add --renormalize .` in one commit (a009577, 48 files). Every checkout is now LF on every platform. **Diagnostic that catches this class of bug:** `git ls-files --eol | grep i/crlf` shows which committed files still carry CRLF in the index. **S4 verification (this session):** image built from `python:3.13-slim` + `uv sync --frozen` → `Python 3.13.15`, `deps ok`, entrypoint creates `/app/uploads/{books,covers,audio,vids}` + `/app/data` at startup.
